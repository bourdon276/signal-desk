# 小项目复盘：减少无效搜索消耗

日期：2026-10-13。

## 做了什么

- 自动搜索同一公开对象、方向、来源集合与窗口的成功尝试，间隔默认12小时，包括零匹配结果；失败间隔6小时。手动搜索缓存仍为非空6小时、空15分钟、失败5分钟，用户无需等待自动周期。
- 全站默认日20 credits中，自动采集最多15次，预留5次供手动与问答补搜。日、月、用户与自动计数在同一事务中预留，失败全部回滚。实际供应商请求的不确定失败仍保守记为已消耗。
- 调度按对象轮换，确保不同对象各获得一次机会后再处理同对象额外方向。有效缓存和自动间隔中的计划不占任务位置。
- 阅读台用当前预算记录区分自动暂停、全站日上限、全站月上限；显示当前账号剩余手动次数。自动暂停继续运行RSS和正文补读。
- 新增完成时间、间隔等待数量及自动/手动余额记录，便于追踪重复消耗；不改来源、密钥或总费用上限。

## 问题与解决

1. 零匹配只缓存15分钟，每小时轮询会再次付费。将后台采集间隔与手动缓存分开，避免零结果导致频繁重复搜索。
2. 自动计划先用完全站日额度后，用户无法主动补搜。增加自动日计数与预留，仍由全站日/月上限兜底；历史已消耗额度保留，不能凭本地计数释放供应商费用。
3. 个别对象有多个兴趣方向，按简单列表排序可能连续占多个位置。以对象分组轮换，先扩大对象覆盖，再深化方向。
4. 仅读取最后采集轮次的耗尽字段会过时。页面预算状态改为实时读取现有计数，并正确区分月上限与日上限。

## 验证

`scripts/eval/search_budget_regression.py` 使用临时SQLite、空结果供应商替身，不连接生产数据库或外部搜索。覆盖：3个关注各一次、空结果过期后不重复付费、自动拒绝原子回滚、预留手动请求成功、全站日/月上限拒绝、12小时后允许重搜、失败6小时等待。该离线回归通过，前端构建和修改文件静态检查通过。

这验证的是预算和调度行为，不能证明新闻召回率上升。线上需观察下一预算日的新增、匹配、正文可读率，以及真实用户兴趣判断。自动周期变长意味着高频新闻可能稍后才补搜；手动入口、RSS与已收录正文仍可使用。旧搜索缓存缺少完成时间时，首次兼容轮次可能执行一次，然后进入新间隔。
